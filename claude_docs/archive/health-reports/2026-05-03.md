## High (fix this week)

### H-001 — STRIPE_CONNECT_WEBHOOK_SECRET set to literal placeholder
**File:** `packages/backend/.env` line 10
**Finding:** `STRIPE_CONNECT_WEBHOOK_SECRET=[PLACEHOLDER — See instructions below]`
**Risk:** When Stripe Connect (POS payment) webhook events arrive, `stripe().webhooks.constructEvent()` is called first with the platform secret (fails, by design), then falls back to `connectSecret`. With a literal placeholder string as the secret, `constructEvent` throws a signature mismatch and the webhook returns 400. If Stripe Connect / POS payouts are live or being tested, these events are silently dropped.
**Fix:** Retrieve the real Connect webhook signing secret from Stripe Dashboard → Webhooks → Connect endpoint → Signing secret, and replace the placeholder in Railway environment variables.
**Affected code:** `packages/backend/src/controllers/stripeController.ts` lines 597–622

### H-002 — Fraud signal routes expose full user objects to non-admin organizers
**File:** `packages/backend/src/routes/fraud.ts`
**Finding:** Routes `GET /api/fraud/sale/:saleId` and `POST /api/fraud/signals/:signalId/review` use only `authenticate` middleware (no `requireAdmin`). Inside `fraudController.ts` lines 168 and 224, the queries use `include: { user: true }` — returning the full user row (including email, passwordHash reference, role, metadata) to any authenticated organizer who calls these endpoints.
**Risk:** Any logged-in user can enumerate fraud signals and retrieve full user PII for users who triggered those signals.
**Fix:** Add `requireAdmin` middleware to fraud routes, OR scope the query to `select: { id: true, name: true }` and verify the requesting organizer owns the referenced sale.

- `services/pricingEngine/adapters/ebay.ts` (2 TODOs — "Integrate with existing fetchEbayPriceComps")
