### Issues Found

#### dashboard.tsx

- **[MEDIUM] No error state for sales data fetch failure** — `dashboard.tsx:145` — `salesData` is initialized with `= []` as its default and `isError` is never destructured from the `useQuery`. When `/sales/mine` returns a network error or 5xx, `salesData` silently stays `[]`, `getDashboardState()` returns `'new'`, and a veteran organizer with many sales sees the "Welcome to FindA.Sale Organizer" new-user hero and zero buttons for existing sales. This is a confusing data-loss appearance with no user feedback. Fix: destructure `isError: salesDataError` from the query and render an inline error callout (e.g., "Couldn't load your sales — please refresh") instead of falling through to the new-user state. — **Severity: medium**

- **[LOW] `window.confirm()` for destructive sale actions** — `dashboard.tsx:1124,1538,1655` — Closing a live sale and reopening ended sales use `window.confirm()` dialogs. This pattern was flagged in last week's spot-check (`add-items/[saleId].tsx:2174`). The rest of the app uses modals and toasts for confirmations. Native `window.confirm()` is visually inconsistent, unstyled, blocks the JS thread, and cannot be dismissed with the app's own Escape-key patterns. — **Severity: low**

- **[LOW] Missing `aria-label` on workspace welcome banner dismiss button** — `dashboard.tsx:602` — The ✕ close button on the "Welcome to [workspace]!" banner has no `aria-label` attribute. A screen reader would announce it as an unlabeled button. Compare to the tier-lapse banner dismiss button at line 768 which correctly has `aria-label="Dismiss banner"`. Fix: add `aria-label="Dismiss welcome message"` to the button at line 602. — **Severity: low**

- **[LOW] `window.location.reload()` used after sale reopen actions** — `dashboard.tsx:1542,1660` — After reopening an ended sale, both the "between sales" section and the "other sales" section trigger `setTimeout(() => window.location.reload(), 1000)`. This causes a full-page flash and discards any open modals or dropdown state. Other post-action flows use `queryClient.invalidateQueries` (see `edit-sale` save mutation). The close-sale action at line 1128 navigates to the settlement page (no reload needed). The reopen actions should instead call `queryClient.invalidateQueries({ queryKey: ['organizer-sales'] })` for a seamless update. — **Severity: low**

#### edit-sale/[id].tsx

- **[MEDIUM] No error state when sale fetch fails or sale not found** — `edit-sale/[id].tsx:98` — `isError` is not destructured from the `useQuery` for `/sales/${id}`. When the API returns 404 (deleted sale), 403 (unauthorized), or a network error, loading completes with `sale = undefined`. The component skips the loading skeleton (since `isLoading` is now false) and renders the full edit form with empty formData defaults: blank title, blank description, empty address. An organizer navigating to a stale link gets a seemingly functional form they can "submit", which fails with a generic toast error. Fix: add `isError: saleError` to the query destructure and render a "Sale not found" error state below the loading guard (after line 418). — **Severity: medium**

- **[LOW] `window.confirm()` for publish/close/reopen actions** — `edit-sale/[id].tsx:346` — `handleToggleSaleStatus()` uses `window.confirm()` for confirming publish, close-early, and reopen actions. Same pattern flagged above and in last week's report. The edit-sale flow is the highest-stakes place to confirm publish — a proper modal with clear consequences ("Your sale will be live to shoppers immediately") would be more appropriate here than a browser confirm dialog. — **Severity: low**

- **[LOW] 13 form inputs lack explicit `id`/`htmlFor` label associations** — Multiple locations — Title, Description, Address, City, State, ZIP, Start Date, End Date, Start Time, End Time, Sale Type, and note fields all use `<label>` + `<input>` associated by DOM nesting only (no `id` on input, no `htmlFor` on label). Contrast with `neighborhood` input which correctly uses `id="neighborhood"` and `htmlFor="neighborhood"` (line 698). Screen readers generally handle implicit nesting, but this is not strict WCAG 2.1 SC 1.3.1 compliance. `create-sale.tsx` was clean on this last week — inconsistency exists across the organizer flow. Fix: add matching `id`/`htmlFor` pairs to all remaining label-input pairs. — **Severity: low**

### Clean

**dashboard.tsx:**
- **Correct `typeof window` / `useEffect` guards everywhere** — All `localStorage` reads in `useState` initializers at lines 110–120 are gated with `if (typeof window === 'undefined') return null/false`. All `window.*` event listeners are inside `useEffect` with cleanup. No SSR-unsafe accesses found.
- **Three-state dashboard (new/active/between)** — All three states have meaningful UI: new organizer gets the welcome hero with step-by-step path; active organizer gets sale status widget + quick actions; between-sales organizer gets congratulations + past sales archive. No blank or dead-end states.
- **Loading skeleton** — Lines 481–494: loading state renders 4 skeleton elements (header, 3 stat cards) while auth + sales data load. Consistent with rest of organizer flow.
- **Multiple secondary query failures degrade gracefully** — `analyticsData`, `orgProfile`, `tierData`, `statsData`, `holdCountData` all use optional chaining and default values. Widgets that depend on these simply don't render rather than throwing. No unhandled query errors visible to users.
- **Tier limit (409) specific error handling** — Lines 1545–1551: sale reopen respects the concurrent sales gate with a specific toast message citing current vs. allowed count. Not a generic error.
- **Modal and overlay close handlers complete** — Flash Deal, Social Post Generator, Boost modal, QR modal all have `onClose`/`onCancel` props wired to state setters. No orphaned open modals.
- **No console.log in this file** — Only `console.error` on caught exceptions (clone, close, reopen failures). Acceptable error logging.
- **No hardcoded placeholder text** — No "Coming soon", "TODO", or Lorem Ipsum in rendered JSX.
- **No `<img>` tags missing `alt=`** — All images are `<Image>` components from Next.js or use the `alt` attribute.

**edit-sale/[id].tsx:**
- **Loading skeleton present** — Lines 403–418: loading state shows 5 skeleton elements matching the form structure.
- **Mutation error handling consistent** — `updateMutation.onError`, `markdownConfigMutation.onError`, `handleCloneSale` catch block, `handleToggleSaleStatus` catch block, and `handleSendApproachNotification` catch block all show specific toast messages.
- **`formInitialized.current` guard prevents background refetch resets** — Once the form is populated from the fetched sale, background refetches no longer overwrite the user's in-progress edits. Good defensive pattern.
- **`window`/`localStorage` usage safe** — Line 346 `window.confirm` and line 868 `window.location.origin` are inside event handlers (not render path). No SSR-unsafe bare accesses.
- **Tier limit upgrade flow wired end-to-end** — 409 on publish triggers `tierLimitError` state which shows a persistent amber callout with a direct upgrade link. Not just a toast.
- **À La Carte publish flow correct** — SIMPLE-tier publish triggers `AlaCartePublishModal` before any API call. On payment success, `handleAlaCarteSuccess` patches status and shows the publish celebration. Correct gate before the publish action.
- **Auto-geocoding on load** — If a sale has address fields but null lat/lng, the page auto-triggers geocoding on load and patches coordinates silently. Good zero-friction behavior for sales created before geocoding was added.
- **No hardcoded placeholder text in rendered UI** — Textarea placeholders ("Start typing or select...", "e.g., Park in back lot...") are instructional helpers, not UI copy.
