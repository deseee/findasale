**SHOPPER DASHBOARD:**

- **[MEDIUM] QR panel permanently open with no close button** — `qrOpen` state initializes `true` and `setQrOpen` is never called anywhere else in the component. The inline QR panel (lines 474–490) occupies significant above-the-fold real estate and cannot be dismissed. The QR modal (triggered by ActionBar) is separate and works correctly. The inline panel is stuck open on every dashboard load. — `dashboard.tsx:134, 474` — severity: **medium**

- **[MEDIUM] Tab navigation lacks ARIA semantics** — The four dashboard tabs (Overview, Subscribed, Pickups, Brands, lines 571–593) use plain `<button>` elements with no `role="tablist"` on the container, no `role="tab"` on the buttons, and no `aria-selected` attribute. Screen readers have no way to announce these as tab controls or communicate which tab is active. — `dashboard.tsx:571–593` — severity: **medium**

- **[MEDIUM] RankHeroSection shows permanent skeleton on XP fetch failure** — The render condition on line 460 is `xpProfile && !xpLoading`. When the fetch fails, `xpLoading` becomes `false` and `xpProfile` is `undefined`, so the condition renders the `<Skeleton>` indefinitely. The `xpError` flag is included in the `hasError` banner (line 300) but the banner is non-specific ("Something went wrong loading your dashboard. Please refresh.") and does not make it obvious that the rank section itself failed. User sees a frozen skeleton under a generic banner. — `dashboard.tsx:460–470` — severity: **medium**

- **[LOW] `window.location.reload()` on payment/hold actions** — `ClaimCard` callbacks on lines 620 and 624 use full page reloads after payment success and hold release. This causes a full-page flash, loses scroll position, and re-fetches everything. Should use `queryClient.invalidateQueries(['pending-invoices'])` instead. Not broken, just jarring UX. — `dashboard.tsx:620, 624` — severity: **low**

- **[LOW] `getRankCopy()` function is dead code** — Defined on lines 320–368 but never called anywhere in the component. Also contains a logic bug: uses `RANK_THRESHOLDS[rank]` (the XP to reach the current rank, already exceeded) rather than `NEXT_RANK_THRESHOLDS[rank]` to compute `xpUntilNext`, so all computed values would be ≤ 0. Since the function is never called, this has no user impact today — but dead code with a latent bug is a hazard. — `dashboard.tsx:320–368` — severity: **low**

- **[LOW] `xpPercent` prop passed to `RankHeroSection` but unused** — The prop is typed (line 11 of RankHeroSection) and destructured (line 132), but the component uses its own internal calculation (`calculatedXpToNext` from `guildXp` and `nextRankThreshold`) and `RankProgressBar` computes its own clamped percentage internally. The prop is always a no-op. Low risk but adds confusion and unnecessary computation at the call site. — `dashboard.tsx:465, RankHeroSection.tsx:11,132` — severity: **low**

- **[LOW] `hasSavedItems` declared but never used** — `const hasSavedItems = false` on line 387 is assigned once and never referenced in any conditional or JSX. Dead variable. — `dashboard.tsx:387` — severity: **low**
