### Issues Found

#### create-sale.tsx

- **[LOW] Unstyled loading state** — `create-sale.tsx:167` — `if (authLoading) return <div>Loading...</div>;` renders plain unstyled text. All other loading states in the organizer flow use `<Skeleton>` components. Minor cosmetic inconsistency for first-time organizers waiting on auth. — **Severity: low**

- **[LOW] Dark mode: form input backgrounds match page background** — `create-sale.tsx:174,223,333,338,348` — The outer page wrapper is `dark:bg-gray-800` and every input also uses `dark:bg-gray-800`. In dark mode, inputs are distinguishable only by their `dark:border-gray-600` border. On lower-contrast monitors, inputs and the page background merge visually. Compare to add-items which wraps the form in a distinct `dark:bg-gray-800` card on a `dark:bg-gray-900` page, creating proper layer separation. — **Severity: low**

#### add-items/[saleId].tsx

- **[HIGH] React Rules of Hooks violation — useMutation called after conditional returns** — `[saleId].tsx:511–519,525,570,588` — Three `useMutation` hooks (`createMutation` at line 525, `deleteMutation` at line 570, `bulkUpdateMutation` at line 588) are defined AFTER the auth guard conditional return at lines 511–514 and the saleId guard at lines 516–519. React requires hooks to be called in the same order on every render. On any render where the auth guard fires (`!authLoading && !user?.roles?.includes('ORGANIZER')`), React returns early and the three mutation hooks are never called — producing a hooks count mismatch. The file comment at line 424 correctly flags this rule but the mutations are still placed after the guard. Fix: hoist all three `useMutation` definitions to before line 511, alongside the existing `useQuery` hooks at lines 426–446. — **Severity: high**

- **[HIGH] Second saleId validation useEffect also placed after conditional returns** — `[saleId].tsx:1292–1301` — A second `useEffect` that validates `saleId` and shows a "Sale not found" toast is positioned after the auth guard (line 511) and saleId guard (line 516). This is a second hooks violation — in any render where either guard fires, this effect is not reached, producing a React hooks count mismatch. The first saleId check (lines 448–453) is correctly placed before the guards. The duplicate at 1292 should be merged into the first or removed. — **Severity: high**

- **[MEDIUM] `window.confirm()` used for single-item delete confirmation** — `[saleId].tsx:2174` — Individual item deletion uses `window.confirm(...)`, a native browser dialog. The same anti-pattern was flagged last week for `alert()` in `shopper/dashboard.tsx`. A well-designed `BulkDeleteConfirm` modal already exists in the file (imported at line 47, used at line 2327). The single-item delete should use a similar inline confirmation UI or a brief "Deleted — Undo" toast, not a blocking native dialog. — **Severity: medium**

- **[MEDIUM] Multiple `console.error` calls in production code paths** — `[saleId].tsx:971,1035,1089,1125,1176` — Five `console.error` calls appear in the rapidfire upload pipeline, quality modal resume handler, and face detection resume handler. These are user-facing code paths (not just dev utilities) and will surface in every organizer's browser dev tools. `console.warn` at line 1231 (poll network error) is acceptable as polling infrastructure, but the error-path calls should be replaced with silent failure or structured telemetry. — **Severity: medium**

- **[LOW] `URL.createObjectURL(pendingFaceBlob)` created on every render** — `[saleId].tsx:1911` — Inside the JSX, `URL.createObjectURL(pendingFaceBlob)` is called inline as the `previewUrl` prop value. This runs on every render of the component while the face detection overlay is open, creating a new object URL each time without revoking the previous one. Over a camera session with multiple re-renders (uploads, state updates), this leaks browser memory. Fix: derive the URL in a `useEffect` or `useMemo` and revoke on cleanup. — **Severity: low**

- **[LOW] Camera tab heading uses fetched item count, not live rapidItems count** — `[saleId].tsx:1793` — The camera section heading reads `items.length > 0 ? '📷 Add More Photos' : 'Capture with Camera'`. `items` comes from the react-query fetch (database records). During an active camera session, newly captured photos appear in `rapidItems` before the query refetches. An organizer who just captured 10 items but hasn't navigated away will see "Capture with Camera" (heading says zero items) until the next query cycle. Should also check `rapidItems.length > 0` in the condition. — **Severity: low**

### Clean

**create-sale.tsx:**
- **Hooks ordering correct** — All hooks (`useRouter`, `useAuth`, `useToast`, `useState`, `useEffect`) are called unconditionally before any conditional returns. No hooks violation.
- **Inline validation** — Date validation errors appear inline below fields (not only as toasts) and respect the `touchedFields` set so errors don't flash before the user has touched the field. Good UX pattern.
- **Tier limit error state** — `TIER_LIMIT_EXCEEDED` (409) produces a persistent amber callout block with upgrade CTA, not just a toast. The error persists until dismissed — correct for a blocking condition.
- **Achievement toast timing** — The 1500ms delay before navigation after the first-sale achievement toast is a nice touch that lets organizers read the message before being redirected.
- **All form inputs have associated labels** — Every `<input>` and `<select>` has an `id` that matches a `htmlFor` label or a `<label>` in a flex container. Accessible.
- **SSR safety** — `isClient` state prevents any client-only rendering issues. No `window.*` or `localStorage.*` outside guards.
- **Sale type selector complete** — All 7 sale types (ESTATE, YARD, AUCTION, FLEA_MARKET, CONSIGNMENT, CHARITY, BUSINESS_CORPORATE) are present. No placeholder options.
- **Generate Description error state** — Catch block at line 124 shows a toast on failure rather than swallowing the error silently.

**add-items/[saleId].tsx:**
- **Loading skeleton** — Auth loading state (lines 1351–1363) uses `<Skeleton>` components correctly.
- **Items list loading state** — `itemsLoading` drives a skeleton row set (lines 1920–1925). Consistent with the rest of the organizer flow.
- **Empty state** — Zero-items state (line 2273–2276) shows a meaningful message with direction to use the tabs. Not a blank page.
- **SSR safety** — All `localStorage` reads are inside `useEffect` or guarded by `typeof window !== 'undefined'`. `window.addEventListener` is inside `useEffect` with proper cleanup. `navigator.clipboard` would only be called from event handlers if present in this file (it's not).
- **Bulk operations error handling** — Partial success (207), per-item failures, and skipped items all show distinct toast messages and open `BulkOperationErrorModal` with item-level detail. Solid UX for a complex operation.
- **Accessibility on destructive actions** — Delete button has `aria-label="Delete item"` (line 2181). Select-all checkbox has `aria-label="Select all items"` (line 1941). Tag remove buttons have `aria-label={Remove tag ${tag}}` (line 1717).
- **Voice input gated to PRO tier** — Voice recording button (line 1540) is only shown when `user.organizerTier === 'PRO'`. Prevents confusing UI for non-PRO users.
- **Rapidfire upload pipeline error handling** — Rate limiting (429) and photo-limit-reached (403 + `upgradeRequired`) both produce specific, actionable error messages rather than generic "Upload failed."
- **Walkthrough dismissible cleanly** — Both "Got it" and "Skip for now" paths properly write to localStorage (with SSR guard) and close the modal. Auto-open camera on "Got it" is a good onboarding decision.
- **No hardcoded placeholder text** — No "Coming soon", "TODO", or placeholder strings in rendered UI (the one `showToast('Enhancement coming soon', 'info')` at line 1891 is behind an event handler, acceptable).
