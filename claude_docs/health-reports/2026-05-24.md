## Medium (fix this sprint)

### M-001 — Three internal auth schemes (inconsistency risk)

**Files:** `packages/backend/src/routes/internal.ts`, `packages/backend/src/controllers/internalGeocodingController.ts`, `packages/backend/src/controllers/internalSaleDetailEnrichmentController.ts`, `packages/backend/src/controllers/internalScraperController.ts`

Three different header/secret schemes are in use for internal endpoints:
- `x-internal-secret` + `OUTREACH_SECRET` — `requireSecret` middleware (used by most internal routes)
- `x-scraper-key` + `INTERNAL_SCRAPER_KEY` — checked in-controller (geocoding, sale detail enrichment, scraper ingest)
- Mixed: `scraper/ingest` uses `x-scraper-key` in-controller, while the file header comment says "Protected by x-scraper-key header"

Risk: rotating one secret without the other leaves routes silently protected by a different, potentially stale key. If `OUTREACH_SECRET` is not set in an environment, `requireSecret` fails closed (blocks all requests), but any route relying on an unset `INTERNAL_SCRAPER_KEY` may behave unpredictably.

**Action:** Document all three schemes explicitly in `.env.example`. Ideally consolidate to one middleware. At minimum, ensure all three env vars are present in Railway and local `.env`.

### M-002 — Bounty purchase checkoutUrl returns null (functional gap)

**File:** `packages/backend/src/controllers/bountyController.ts:514`

```ts
checkoutUrl: null, // TODO: integrate Stripe
```

When an organizer approves a bounty submission, the API returns `checkoutUrl: null`. Any frontend flow that attempts to redirect the buyer to Stripe payment for a bounty-matched item will silently fail or need to handle a null URL. This is a functional gap on the bounty purchase path, not just a code comment.

**Action:** Confirm whether the bounty Stripe payment flow is intentionally deferred (add roadmap item) or is an overlooked TODO from feature implementation. If deferred, add a feature-flagged error response instead of null.

### M-003 — Unbounded findMany in non-admin authenticated routes

**Files:** `bountyController.ts`, `affiliateController.ts`, `arrivalController.ts`, `boostController.ts`, `brandFollowController.ts`, `briefingController.ts`, `buyingPoolController.ts`

Several `findMany` calls in organizer/shopper-facing controllers lack a `take` limit. These are currently safe due to `where` clauses scoped by `userId` or `organizerId`, but as user data grows (an organizer with 500+ sales, a shopper with 200+ bounties), these queries will become slow and could impact response times.

Examples:
- `bountyController.ts:108,130,265` — unbounded bounty fetches
- `affiliateController.ts:67,343,416` — unbounded affiliate link/referral fetches
- `arrivalController.ts:167,182` — unbounded subscriber/notification fetches

**Action:** Add `take: 100` (or appropriate limit) with cursor-based pagination to the highest-traffic of these routes. Priority: bountyController (public-adjacent feature), affiliateController (referral dashboard).
