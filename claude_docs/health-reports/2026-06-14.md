## Medium (fix this sprint)

### M-001: POST /api/search/notify — no rate limiter (email write endpoint)
**File:** `packages/backend/src/routes/search.ts` line 531
**Finding:** `router.post('/notify', notifyOnSearch)` has no rate limiter. The `searchLimiter` applied to the GET `/` route is not applied here. The endpoint accepts an email address and writes it to the `SearchNotification` table. No rate limiting means a single IP could flood the table with valid email registrations (unique email+query combos per ON CONFLICT DO NOTHING — but there's no cap on unique emails). The endpoint also implicitly functions as an email existence checker for attackers if they can distinguish "already on the list" from "added."
**Evidence:** `grep -n "notify\|Limiter" routes/search.ts` — line 531 has no middleware between route and handler. `searchLimiter` is imported but only applied to the GET search route.
**Action:** Add `searchLimiter` (or a dedicated `notifyLimiter` at 5/min) before `notifyOnSearch`. One-line fix.

### M-002: 8 npm HIGH/CRITICAL vulnerabilities (persisting — week 2)
**Packages:** `path-to-regexp` (ReDoS, HIGH), `axios` (auth bypass, HIGH), `js-cookie` (cookie injection, HIGH), `esbuild` (binary integrity, HIGH — dev only), `tsx` (transitive esbuild), `semver` (ReDoS, HIGH), `nodemon`/`simple-update-notifier` (transitive semver)
**Evidence:** `npm audit` in `packages/backend` — 8 HIGH/CRITICAL entries confirmed.
**Context:** `path-to-regexp` is transitive from Express (can't easily fix). `esbuild`/`tsx` are dev-only (not in production bundle). `axios` is a runtime dep — upgrade to `>=1.15.1` resolves it. `js-cookie` does not appear to be directly imported in frontend TS files — may be transitive.
**Action:** (1) `pnpm update axios@latest` in backend. (2) Confirm `js-cookie` is not a direct frontend dep — if transitive, check if upgrading the parent resolves it. (3) Track `path-to-regexp` — fix only if Express releases a version that pins a safe version.
**Session added:** This report (week 2 since security audit first flagged these)

## Low (track, fix when relevant)

### L-001: viewers.ts DELETE route — public, no auth
**File:** `packages/backend/src/routes/viewers.ts` line 17
**Finding:** `DELETE /api/viewers/:saleId/:viewerId` removes a viewer presence record with no authentication. Any actor can delete any viewerId if they know the saleId and viewerId (both are transient UUIDs). Risk is limited to presence-count disruption (not data loss). The viewerId would need to be guessed or intercepted.
**Evidence:** `cat routes/viewers.ts` — three routes, zero middleware, DELETE confirmed.
**Action:** Low risk for beta. Consider adding optionalAuthenticate or a short-TTL token check in Phase 2 when viewer counts become product-meaningful.

### L-002: OUTREACH_SECRET and INTERNAL_SCRAPER_KEY absent from local .env
**File:** `packages/backend/.env`
**Finding:** Both vars missing from local `.env`. If also absent from Railway, internal routes protected by these secrets would deny all traffic (graceful failure — undefined !== provided secret). Per S907 these were confirmed present in Railway. The local `.env` gap means local dev cannot test outreach cron or geocoding endpoints.
**Evidence:** `comm -23 env_example.txt env_actual.txt` — both keys absent.
**Action:** Document in `.env.example` that these are Railway-only secrets (not needed for local frontend/backend dev). No security risk.

### L-003: Unbounded findMany in itemController background paths
**File:** `packages/backend/src/controllers/itemController.ts` lines 679, 2547, 2664, 3007, 3321, 3368
**Finding:** Six `findMany` calls without `take:` in itemController. Sampled: line 679 (item list — context needed), line 3007 (`rareItems`), line 3321 (`similarItems`). These appear to be scoped by sale/organizer where clause (bounded by organizer's item count), not unbounded table scans. Low risk in beta.
**Evidence:** `grep -n "findMany" controllers/itemController.ts | grep -v "take:"` — 6 matches confirmed.
**Action:** Track; no immediate action. If any serve public-facing endpoints without a where clause, upgrade to M-001 in next report.
